# Implement Task

Read an implementation plan produced by the `plan-task` skill and execute it step-by-step, updating the external task status at the start and end of implementation.

## When to Use

- A plan file already exists at `.task/plan.md` (created by `plan-task`)
- You want to execute that plan and ship the code changes
- The task tracker should reflect progress automatically

## Procedure

### 0. Locate the Plan File

Look for `.task/plan.md` relative to the current workspace root.

**If the file is missing:** stop and tell the user to run `plan-task` first.

### 1. Read Task Context

1. Read `.task/plan.md` in full.
2. Read `.task/task.json` and extract:
   - `taskLink` and `taskSource` — used for status updates in Steps 2 and 7.
   - `scope` and `project` — used to determine the default working directory for commands.
3. Understand the plan structure — identify the ordered list of implementation steps, any dependencies between them, and the acceptance criteria.
4. Set working directory context:
   - **Project-scoped** (`scope` = `"project"`): default working directory for commands is `<worktree-root>/<project>`.
   - **Repo-scoped** (`scope` = `"repo"`): default working directory is the worktree root.

### 2. Update Task Status → In Progress

**Only if `taskLink` and `taskSource` are present in `task.json`.**

1. Use `tool_search_tool_regex` to discover the appropriate **update** tool in the MCP namespace stored in `taskSource`.
2. Update the task status to **"In Progress"** (or the closest equivalent the tool supports, such as setting the `State` field to `Active` for ADO work items).
3. If no update tool is available, log a warning and continue — do not block implementation.

### 3. Set Up the Todo List

Create a todo list from the plan steps so progress is visible throughout execution. Each plan step becomes a todo item. Mark all as `not-started` initially.

### 4. Execute the Plan

For each step in the plan, in order:

1. Mark the corresponding todo as `in-progress`.
2. Implement the changes described in that step:
   - Read relevant source files before making edits.
   - Follow the plan's guidance on which files to create or modify.
   - Run any commands the plan specifies (tests, builds, migrations, etc.).
3. Validate the step:
   - Check for compile/lint errors after edits.
   - Run any tests mentioned in the plan step.
4. Mark the todo as `completed` before moving on.

**If a step is blocked or unclear:**
- Re-read the plan for additional context.
- Search the codebase for similar patterns.
- If truly stuck, stop and ask the user for clarification rather than guessing.

### 5. Final Validation

After all plan steps are complete:

1. Run the full test suite if the plan specifies one, or run tests relevant to the changed files.
2. Check for lint/compile errors across all modified files.
3. Fix any issues found.

### 6. Review Changes

Follow the review instructions in `.github/prompts/PR_Review.prompt.md` to self-review all changes made during implementation. Address any feedback. If something is flagged but you believe it's best not to address, explain why.

### 7. Update Task Status → Ready for Review

**Only if `taskLink` and `taskSource` were present in `task.json`.**

1. Use the same MCP update tool discovered in Step 2.
2. Update the task status to **"Ready for Review"** (or the closest equivalent, such as setting the `State` field to `Ready for Review` for ADO work items).
3. If the update fails, warn the user but do not fail the overall workflow.

### 8. Summary

Report:

- Number of plan steps completed
- Files created or modified
- Tests run and their results
- Whether the task status was updated (and to what values), or that no task link was found
- Any issues encountered or deviations from the plan
